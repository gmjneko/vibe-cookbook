# 阶段一：项目全景

这一阶段的目标是：用户读完以后，能说清楚这个项目是做什么的、属于什么类型、代码怎么组织、各模块怎么协作、一次典型操作在代码里是怎么流转的，并且知道接下来该从哪里读起。这一阶段**不展开讲具体功能**，功能留给阶段二。

## 调查步骤

按顺序进行，每一步都要实际读代码或文件，不要凭印象。

1. **读项目自述。** README、docs 目录、CONTRIBUTING、CHANGELOG 的开头部分。注意文档可能过时，后面要用代码核对。
2. **读依赖清单和构建配置。** 弄清语言、运行环境、核心依赖（以及每个核心依赖在这个项目里承担什么角色）、构建和测试命令、发布形态（发布为包？构建成二进制？部署成服务？）。
3. **看目录结构。** 列出 2 到 3 层目录，识别源码、测试、示例、文档、脚本、配置各在哪里。
4. **找入口。** 应用的 main 函数或启动文件、库的公开导出入口（如 `index.ts`、`__init__.py`、`lib.rs`）、CLI 的命令注册处、服务的路由注册处。
5. **判断项目类型**（见下文）。
6. **划分模块并理清依赖关系。** 读每个顶层模块的入口文件和对外接口，看它 import 了哪些其他模块。
7. **追踪一条主链路。** 选一个最典型的操作，从入口一路读到结束（见下文"一次操作的完整旅程"）。这一步必须逐个函数地读下去，是本阶段最花时间、也最有价值的部分。
8. **收集核心概念。** 在前面的阅读中反复出现的、项目自己定义的抽象和术语。
9. **建立功能清单。** 初步列出项目提供的功能，写进 `_meta.md`，供阶段二使用。识别方法见 `features.md` 中的"建立功能清单"。

## 判断项目类型

项目类型决定了后续怎么讲。常见类型和识别信号：

- **框架**：控制程序的主流程，用户的代码被它调用（控制反转）；有生命周期、扩展点、插件或钩子机制；通常有 `examples/` 和面向使用者的文档。讲解重点是使用方式、扩展点和约定。
- **库**：提供一组能力供调用，用户的代码调用它；以公开 API 为中心。讲解重点是 API 的分组、用法和组合方式。
- **应用**：直接面向最终用户，包含业务领域逻辑，可能有 UI。讲解重点是业务流程、领域模型和数据流。
- **CLI 工具**：以命令和参数为界面。讲解重点是命令结构和每个命令背后的执行流程。
- **服务**：长期运行，对外提供 API。讲解重点是接口、请求处理链路、存储和外部依赖。

很多项目是混合型的（比如一个框架附带了 CLI 脚手架，或者一个 monorepo 里既有库又有应用），这时要说清楚主体是什么、各部分分别是什么类型。判断结果要附上依据，比如"`package.json` 声明了 `exports` 且 `examples/` 下的代码都是通过继承 `BaseHandler` 来接入的，所以它是一个框架"。

## 01-overview.md 的结构

下面是章节的顺序和每一节要回答的问题。章节标题可以根据项目调整措辞，但内容不能缺。篇幅参考：小项目 3000 字左右，大型项目不超过 8000 字。宁可在主链路和架构上写透，也不要在目录说明上铺满。

### 1. 这是一个什么项目

用几段话讲清楚：它解决什么问题；在它出现之前，人们通常怎么解决这个问题、有什么痛点；谁会用它、在什么场景下用；它属于哪种项目类型（附依据）。如果它有知名的同类项目，用一两句话点明它和同类的核心差异，前提是这种差异能从代码或文档中得到确认。

### 2. 先把它跑起来

环境要求、安装依赖、构建、运行、跑测试的具体命令，全部从项目实际的配置文件和脚本中获取。如果是框架或库，给出一个最小可运行示例（优先取自 `examples/` 或 README）。说明跑起来以后应该看到什么现象，这样新人能确认自己成功了。如果有常见的环境坑（特定版本要求、需要额外服务如数据库），一并说明。

### 3. 目录结构

给出裁剪过的目录树（只保留有意义的 2 到 3 层，忽略构建产物和依赖目录），在树中用简短注释标出每个目录的作用。树后面用一两段话说明这个目录组织方式背后的逻辑：是按技术分层组织的，还是按业务功能组织的，还是按包组织的 monorepo；新人找代码时应该怎么利用这个规律。

### 4. 模块划分

逐个介绍核心模块，每个模块写一段：它负责什么、为什么要把这些职责放在一起、对外暴露什么、依赖谁、被谁依赖。非核心模块（工具函数、脚本等）可以合并成一段简述。

然后画一张 mermaid 模块依赖图（节点控制在 15 个以内，过多时按层或按组合并），并说明依赖的方向有什么规律，比如"所有依赖都指向 `core`，`core` 不依赖任何其他模块"，以及这个规律意味着什么。

### 5. 架构设计

讲清楚整体架构：分了哪几层或哪几个大的部件、每一层的职责边界、层与层之间通过什么接口或抽象来交互。重点讲项目中最核心的两三个抽象（比如某个接口、某个基类、某个核心数据结构），它们是理解整个项目的钥匙。

配一张 mermaid 或者 Markdown 纯文本画的架构图。如果项目有明显的设计模式或架构风格（插件架构、事件驱动、管道、分层、微内核等），点明它，并说明它在这个项目里具体是怎么体现的、带来了什么好处和代价。

### 6. 一次操作的完整旅程

挑一个最能代表项目核心价值的典型操作（Web 框架选一次 HTTP 请求，编译器选一次编译，CLI 选最常用的命令，应用选最核心的业务流程），从入口开始，按执行顺序讲它经过的每一个关键步骤：在哪个文件的哪个函数里、做了什么、数据变成了什么样、为什么需要这一步。

链路上最关键的两三个步骤（通常是入口函数和核心分发处），按 `style.md` 中"代码摘录"的格式贴出代码，其余步骤用文字讲清楚并写明文件和函数名即可。配一张 mermaid 时序图。这一节是新人建立"代码是怎么动起来的"直觉的关键，要写得具体，不要停留在"请求经过中间件处理后交给路由"这种层次。

### 7. 核心概念

解释项目自己定义的关键术语和抽象，每个概念写一小段：它是什么、为什么需要它、在代码中对应哪个类型或模块。按理解的先后顺序排列，前面的概念不依赖后面的概念。

### 8. 推荐阅读路线

告诉用户如果想亲自读源码，应该按什么顺序读哪些文件，每一步读完能获得什么认识；哪些目录在入门阶段可以完全跳过。路线控制在 5 到 8 步。

### 9. 功能地图与下一步

简要列出阶段二将会讲解的功能分类（这里可以用列表，只列分类名和一句话说明），然后建议新人接下来看什么。
