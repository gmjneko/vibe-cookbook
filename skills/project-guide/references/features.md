# 阶段二：功能讲解

这一阶段的目标是：用户读完以后，知道这个项目能做哪些事，每件事在什么场景下会用到、怎么用、大致是怎么实现的。深度介于"概览"和"深挖"之间：每个功能讲到用户能正确使用、并知道去哪里看实现的程度，不展开到每个分支和边界情况，那是阶段三的事。

## 开始之前

读 `_meta.md` 和 `01-overview.md`。如果用户在参数里指定了模块名或分类名，只讲这个范围内的功能；没有指定就讲全部。

## 建立功能清单

如果 `_meta.md` 中的功能清单还很粗糙，先把它补完整。"功能"是从使用者角度看到的一项能力，而不是一个文件或一个类。不同类型的项目，功能的来源不同：

- **框架和库**：公开导出的 API、扩展点（插件、钩子、中间件、生命周期回调）、配置项中能开关或改变行为的部分、文档目录中的主题。
- **应用**：用户可见的业务能力（页面、操作、流程），以及支撑它们的关键后台能力（权限、通知、定时任务等）。
- **CLI**：每个命令和子命令，以及跨命令的全局能力（配置文件、输出格式、插件）。
- **服务**：每组 API 及其背后的业务能力，以及鉴权、限流、任务队列等横切能力。

测试目录是发现功能的好线索：测试文件的组织方式往往反映了作者心目中的功能划分。

把功能**按使用者的视角分类**，而不是按目录分类。比如一个 Web 框架可以分成"请求处理""数据校验""错误处理""扩展机制""测试支持"等。每类 3 到 8 个功能比较合适。

功能超过 15 个时，按分类拆分成多个文件（`02-features-<分类>.md`），并且一次只写一到两个分类，写完后告诉用户还剩哪些分类，由用户决定继续写哪一个。

## 每个功能怎么讲

每个功能是一个小节，用连贯的段落写，包含下面这些内容。这是内容要求，不是要你写成"场景：… / 用法：…"这样的字段表单；段落之间要有因果衔接，读起来像一位同事在讲解。

**它解决什么问题。** 从一个具体的场景切入：开发者或用户遇到了什么情况、如果没有这个功能会怎样。让读者先感受到需要，再介绍功能本身。

**怎么用。** 给一段最小可用的代码示例或操作步骤，紧接着解释示例中的关键部分。示例来源优先级：项目测试 > `examples/` > 官方文档 > 项目内部对这个功能的真实调用 > 你自己写的（必须对照 API 签名核对）。注明示例出处。

**实现思路。** 用一两段话讲清楚它在内部大致是怎么工作的：入口在哪个文件的哪个函数，核心逻辑分几步，依赖了哪些其他模块或核心抽象。把最核心的那段代码按 `style.md` 中"代码摘录"的格式贴出来（这一阶段通常一段就够；代码不长就整段贴出，较长时才按规则省略），让读者不用翻源码也能看懂它是怎么工作的。

**与其他功能的关系。** 如果它经常和别的功能配合使用，或者和某个功能容易混淆，说明它们的区别以及各自该在什么时候用。

## 框架和库的额外要求

如果项目是框架或库，使用方式是用户最关心的部分，要写得更充分：

- 除了最小示例，再给出一到两个**贴近真实开发场景的示例**，展示这个功能在实际项目里通常是怎么和其他功能组合使用的，并说明为什么在这种场景下要这样用。
- 写清楚**什么时候不该用它**，或者有什么更合适的替代方案。
- 有多种用法时（比如同一件事可以用配置、装饰器或者手动注册三种方式实现），说明每种方式适合什么场景、各有什么取舍，而不是只罗列三种写法。
- 指出新手最容易犯的错误，前提是这些错误能从代码逻辑、文档警告、issue 或测试用例中得到依据。

## 应用类项目的额外要求

如果项目是应用或服务，功能讲解要更侧重业务流程：

- 讲清楚这个业务功能涉及哪些领域对象、它们的状态如何变化，必要时配一张 mermaid 状态图或流程图。
- 讲清楚一次操作的数据流向：从界面或接口进来，经过哪些层，读写了哪些存储或外部服务。

## 02-features.md 的结构

开头一段话介绍功能的整体分类，以及这些分类之间的关系（比如"请求处理是主干，校验和错误处理是挂在主干上的环节，扩展机制则允许你改写其中任何一环"）。然后按分类组织：每个分类先用一段话说明这一类功能的共同目的，再逐个讲功能。

结尾给出推荐深挖的功能（从刚讲过的功能中挑两三个），说明推荐理由：比如它是理解整个项目的关键、它的设计很有代表性、或者它是使用中最容易出问题的地方。

写完后更新 `_meta.md` 中功能清单的"已讲解"一列。
