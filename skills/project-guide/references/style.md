# 写作规范

读者是一个刚接触这个项目的新人。你写的东西应该像一位耐心的资深同事在白板前讲解：有来龙去脉，有具体例子，有因果关系。要避免的是模型最常见的默认输出：一串没有解释的要点列表。

## 核心规则

**用段落讲解，不用要点堆砌。** 解释性的内容（功能是什么、为什么需要、怎么工作、为什么这样设计）一律写成连贯的段落。一个段落围绕一个意思展开，段落之间用因果、转折、递进连接起来。如果你发现自己在写"功能：… / 场景：… / 实现：…"这样的字段式结构，或者连续三个以上每条只有半句话的列表项，就改写成段落。

**列表和表格只用于本身就是清单性质的内容。** 允许使用的场景：目录树、命令清单、配置项及其含义、API 参数说明、`_meta.md` 中的索引、操作步骤（每一步都有明确的先后顺序）。即使在这些场景中，如果某一项需要解释"为什么"，也要在列表外用段落展开。

**先讲为什么，再讲是什么，最后讲怎么做。** 介绍任何功能或设计，都从它要解决的问题或面对的场景开始。读者先理解了需要，才能理解方案。

**具体胜过抽象。** 用具体的场景、具体的代码、具体的数据流转来说明。"中间件机制提供了灵活的扩展能力"没有信息量；"可以在请求到达路由之前统一校验 token，而不用在每个处理函数里重复书写"才有。

**术语第一次出现时要解释。** 项目自己定义的概念，第一次出现时用一句话说明它是什么、对应代码中的哪个类型。之后保持同一种叫法，不要一会儿叫"处理器"一会儿叫"handler"、一会儿叫"回调"一会儿叫"Callback"。

**每个关键结论都有出处。** 写 `src/router/match.ts:42` 或者"`src/router/match.ts` 中的 `matchRoute`"。推测的内容标注"（推测）"，并说明你是根据什么推测的。

## 要避免的写法

- 空洞的形容词和宣传腔："强大的""灵活的""优雅的""高性能的""开箱即用"。如果某个特性确实好，用具体事实来说明它好在哪里。
- 没有信息量的开场和总结："本节将介绍……""综上所述……""总的来说，这是一个非常优秀的设计"。直接进入内容。
- 泛泛而谈的设计原则："体现了开闭原则""实现了高内聚低耦合"。除非你能具体指出代码中的哪个决定因此而做出、带来了什么实际效果。
- 大段粘贴源码。摘录只保留最能说明问题的几行，其余用文字描述并给出位置。
- 对着代码逐行翻译："第一行定义了变量 x，第二行调用了函数 f"。要讲的是这段代码在做什么事、为什么这样做。

## 正反示例

下面以一个虚构的 Web 框架的"中间件"功能为例（路径和代码都是虚构的，只用来演示写法）。阶段一、阶段三以及对话回复的示例见 `examples.md`，它们用的是同一个虚构框架。

### 不要这样写

> ### 中间件
>
> - **功能**：在请求处理前后执行自定义逻辑
> - **特点**：灵活、可组合、支持异步
> - **使用场景**：
>   - 鉴权
>   - 日志
>   - 错误处理
> - **实现**：基于洋葱模型，通过 `compose` 函数组合
> - **用法**：`app.use(fn)`

问题在于：每一条都正确，但新人读完仍然不知道什么时候该用中间件、"洋葱模型"是什么意思、`compose` 做了什么、`fn` 应该怎么写。这是一份目录，不是讲解。

### 要这样写

> ### 中间件
>
> 假设有一个应用有二十个接口都需要校验登录状态。如果在每个处理函数开头都写一遍校验 token 的代码，不仅重复，而且一旦校验逻辑要改，需要改二十个地方。中间件就是为这类"很多请求都要做的同一件事"准备的：你把校验逻辑写成一个函数注册到应用上，框架会让每个请求在到达处理函数之前先经过它。
>
> 一个中间件是一个接收 `ctx` 和 `next` 的异步函数。`ctx` 是这次请求的上下文，包含请求和响应对象；`next` 则代表"后面所有的中间件和最终的处理函数"。下面是项目测试中的一个计时中间件（`test/middleware.test.ts:15`）：
>
> ```ts
> app.use(async (ctx, next) => {
>   const start = Date.now();
>   await next();
>   ctx.set('X-Response-Time', `${Date.now() - start}ms`);
> });
> ```
>
> 关键在 `await next()` 这一行：它之前的代码在请求"进入"时执行，之后的代码在后面的处理全部完成、请求"返回"时执行。多个中间件因此像洋葱一样层层包裹，请求从外向内穿过每一层，响应再从内向外穿回来。这也决定了注册顺序很重要：如果你希望错误处理中间件能捕获所有其他中间件抛出的异常，就必须最先注册它，让它位于洋葱的最外层。
>
> 实现上，`app.use` 只是把函数追加到一个数组里（`src/application.ts:58`）。真正的组合发生在 `src/middleware/compose.ts` 的 `compose` 函数中：它返回一个从第 0 个中间件开始执行的函数，并把"执行第 i+1 个中间件"包装成 `next` 传给第 i 个。这里还有一个容易被忽略的保护：如果同一个中间件里调用了两次 `next`，`compose` 会直接抛出错误（`compose.ts:21`），因为重复执行后续链路几乎总是 bug。
>
> 中间件适合与具体路由无关的横切逻辑。如果某段逻辑只对少数几个接口生效，更合适的做法是使用路由级的守卫（见"路由守卫"一节），否则你就得在中间件里自己判断路径，这又回到了到处写条件分支的老问题。

这个版本先从一个具体的痛点讲起，再介绍概念；示例有出处；解释了示例中最关键的一行，并由此引出"注册顺序很重要"这个实用结论；实现部分给出了位置，并点出了一个不显眼但重要的细节；最后说明了什么时候不该用中间件。这就是每个功能讲解应该达到的样子。
