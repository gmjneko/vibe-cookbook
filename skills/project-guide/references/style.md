# 写作规范

读者是一个刚接触这个项目的新人。你写的东西应该像一位耐心的资深同事在白板前讲解：有来龙去脉，有具体例子，有因果关系。要避免的是模型最常见的默认输出：一串没有解释的要点列表。

## 核心规则

**用段落讲解，不用要点堆砌。** 解释性的内容（功能是什么、为什么需要、怎么工作、为什么这样设计）一律写成连贯的段落。一个段落围绕一个意思展开，段落之间用因果、转折、递进连接起来。如果你发现自己在写"功能：… / 场景：… / 实现：…"这样的字段式结构，或者连续三个以上每条只有半句话的列表项，就改写成段落。

**列表和表格只用于本身就是清单性质的内容。** 允许使用的场景：目录树、命令清单、配置项及其含义、API 参数说明、`_meta.md` 中的索引、操作步骤（每一步都有明确的先后顺序）。即使在这些场景中，如果某一项需要解释"为什么"，也要在列表外用段落展开。

**先讲为什么，再讲是什么，最后讲怎么做。** 介绍任何功能或设计，都从它要解决的问题或面对的场景开始。读者先理解了需要，才能理解方案。

**具体胜过抽象。** 用具体的场景、具体的代码、具体的数据流转来说明。"中间件机制提供了灵活的扩展能力"没有信息量；"可以在请求到达路由之前统一校验 token，而不用在每个处理函数里重复书写"才有。

**术语第一次出现时要解释。** 项目自己定义的概念，第一次出现时用一句话说明它是什么、对应代码中的哪个类型。之后保持同一种叫法，不要一会儿叫"处理器"一会儿叫"handler"、一会儿叫"回调"一会儿叫"Callback"。

**每个关键结论都有出处，关键实现要贴出代码。** 只是顺带提到、给读者指个路的地方，写"`src/router/match.ts` 中的 `matchRoute`"即可；正在讲解的关键实现，必须按下面"代码摘录"一节的格式把代码贴出来，不能只留一个 `src/router/match.ts:42` 让读者自己去翻。

## 代码摘录

读者手边不一定开着源码，只给行号等于让他中断阅读去翻文件，而且行号会随代码变动失效。所以讲到关键实现时，直接把代码放进正文。

**代码不长就整段贴出，不做省略。** 二十行以内的函数或代码段，原样完整贴出来。省略本身有代价：读者要相信你的注释准确概括了被跳过的部分，所以能完整贴出的就不要省略。

```ts title="compose.ts"
export function compose(middleware: Middleware[]) {
  return function (ctx: Context, next?: Next) {
    let index = -1;
    return dispatch(0);

    function dispatch(i: number): Promise<void> {
      if (i <= index) return Promise.reject(new Error('next() called multiple times'));
      index = i;
      let fn = middleware[i];
      if (i === middleware.length) fn = next;
      if (!fn) return Promise.resolve();
      try {
        return Promise.resolve(fn(ctx, dispatch.bind(null, i + 1)));
      } catch (err) {
        return Promise.reject(err);
      }
    }
  };
}
```

**代码较长时才省略，而且省略不能影响读者对逻辑的理解。** 被省略的只能是对当前要讲的逻辑没有影响的部分，比如日志、调试输出、开发模式下的警告、与当前话题无关的辅助功能。省略处写成"注释 + `...`"，注释说明这几行做了什么：

```ts title="application.ts"
listen(...args: ListenArgs) {
  // 开发模式下把已注册的路由表打印到控制台，方便调试
  ...

  this.router.assertNoConflict();
  const stack = [...this.middleware, this.router.middleware()];
  this.fn = compose(stack);

  // 依次调用每个插件的 onReady 钩子；任一钩子抛错都会中止启动，不会走到下面的 createServer
  ...

  const server = http.createServer((req, res) => this.handle(req, res));
  return server.listen(...args);
}
```

注意第二处省略：插件钩子会影响后续流程（抛错就中止启动），所以注释把这个影响写了出来。读者只看摘录和注释，仍然能正确说出 `listen` 的完整执行过程。

具体规则：

- **代码块开头写"语言标记 + `title`"**，如 ` ```ts title="compose.ts" `。语言标记保证语法高亮，`title` 标出代码来自哪个文件。项目里有同名文件、容易混淆时，`title` 写相对路径，如 ` ```ts title="src/middleware/compose.ts" `。
- **摘录必须与源码一致。** 保留的行原样照抄，不改变量名、不合并语句、不"顺手简化"逻辑。但可以为了方便理解添加一些额外的注释，但应该在注释前加上标记，例如"// @Comment 此处做了一次隐式的fallback，目的是xxxxx"
- **二十行以内整段贴出。** 只有更长的代码才考虑省略。
- **决定逻辑的代码不能省略。** 以下内容只要和当前讲解的话题相关，就必须保留：分支和循环条件、提前 `return`/`break`/`continue`、抛出或捕获异常的地方、对后面会用到的变量的赋值和修改、返回值的构造、有副作用的调用（写状态、发请求、改共享数据）。
- **省略的注释要写清影响。** 注释用该文件所用语言的注释语法（`//`、`#`、`--` 等），说明被省略的这几行做了什么；如果它们会影响后面的代码（产生了后面用到的变量、可能提前返回或抛错、修改了共享状态），注释里必须点明，比如"解析 header，结果存入 `opts`"。紧接着单独一行 `...`，省略的前后各空一行。不要只写一个光秃秃的 `...`。
- **省略后自检。** 问自己：读者只看这段摘录和注释，能不能正确说出这段代码在各种输入下会怎么执行？如果被省略的部分会改变这个答案，就把它放回来。省略之后依然太长，就直接把这个比较长的代码完整放上来，可以允许长代码出现。
- **代码块前后都要有文字。** 前面说明这段代码在哪个函数里、为什么要看它；后面解释其中最关键的一两行在做什么、为什么这样写。不要贴完代码就接着讲下一件事。
- **自己写的示例不加 `title`。** 只有从项目中摘录的代码才加 `title`；你自己编写的用法示例，只写语言标记（如 ` ```ts `），并按 SKILL.md 的要求对照真实 API 核对。

## 要避免的写法

- 空洞的形容词和宣传腔："强大的""灵活的""优雅的""高性能的""开箱即用"。如果某个特性确实好，用具体事实来说明它好在哪里。
- 没有信息量的开场和总结："综上所述……""总的来说，这是一个非常优秀的设计"。直接进入内容。
- 泛泛而谈的设计原则："体现了开闭原则""实现了高内聚低耦合"。除非你能具体指出代码中的哪个决定因此而做出、带来了什么实际效果。
- 把很长的一大段源码不加取舍地整段粘贴。二十行以内可以整段贴，更长的要按"代码摘录"的规则省略无关部分，或者拆开讲。
- 为了显得简洁，把分支、提前返回、异常处理这类决定逻辑的代码省略掉，只留一句笼统的注释。
- 对着代码逐行翻译："第一行定义了变量 x，第二行调用了函数 f"。要讲的是这段代码在做什么事、为什么这样做。

## 正反示例

下面以一个虚构的 Web 框架的"中间件"功能为例（路径和代码都是虚构的，只用来演示写法）。阶段一、阶段三以及对话回复的示例见 `examples.md`，它们用的是同一个虚构框架。

### 不要这样写

> ### 中间件
>
> - **功能**：在请求处理前后执行自定义逻辑
> - **特点**：灵活、可组合、支持异步
> - **使用场景**：
>   - 鉴权
>   - 日志
>   - 错误处理
> - **实现**：基于洋葱模型，通过 `compose` 函数组合
> - **用法**：`app.use(fn)`

问题在于：每一条都正确，但新人读完仍然不知道什么时候该用中间件、"洋葱模型"是什么意思、`compose` 做了什么、`fn` 应该怎么写。这是一份目录，不是讲解。

### 要这样写

> ### 中间件
>
> 假设有一个应用有二十个接口都需要校验登录状态。如果在每个处理函数开头都写一遍校验 token 的代码，不仅重复，而且一旦校验逻辑要改，需要改二十个地方。中间件就是为这类"很多请求都要做的同一件事"准备的：你把校验逻辑写成一个函数注册到应用上，框架会让每个请求在到达处理函数之前先经过它。
>
> 一个中间件是一个接收 `ctx` 和 `next` 的异步函数。`ctx` 是这次请求的上下文，包含请求和响应对象；`next` 则代表"后面所有的中间件和最终的处理函数"。下面是项目测试中的一个计时中间件：
>
> ```ts title="middleware.test.ts"
> app.use(async (ctx, next) => {
>   const start = Date.now();
>   await next();
>   ctx.set('X-Response-Time', `${Date.now() - start}ms`);
> });
> ```
>
> 关键在 `await next()` 这一行：它之前的代码在请求"进入"时执行，之后的代码在后面的处理全部完成、请求"返回"时执行。多个中间件因此像洋葱一样层层包裹，请求从外向内穿过每一层，响应再从内向外穿回来。这也决定了注册顺序很重要：如果你希望错误处理中间件能捕获所有其他中间件抛出的异常，就必须最先注册它，让它位于洋葱的最外层。
>
> 实现上，`app.use` 只是把函数追加到一个数组里，真正的组合发生在 `src/middleware/compose.ts` 的 `compose` 函数中：
>
> ```ts title="compose.ts"
> function dispatch(i: number): Promise<void> {
>   if (i <= index) return Promise.reject(new Error('next() called multiple times'));
>   index = i;
>   let fn = middleware[i];
>   if (i === middleware.length) fn = next;
>   if (!fn) return Promise.resolve();
>   try {
>     return Promise.resolve(fn(ctx, dispatch.bind(null, i + 1)));
>   } catch (err) {
>     return Promise.reject(err);
>   }
> }
> ```
>
> `try` 里那一行就是洋葱模型的全部秘密：执行第 i 个中间件时，把"执行第 i+1 个"包装成 `next` 传给它。中间件调用 `next()`，链路才会往里走一层；不调用，后面的中间件和处理函数就都不会执行。走到数组末尾时，`fn` 换成外部传入的 `next`，如果也没有，就返回一个已完成的 Promise，最内层的 `await next()` 因此能正常返回，洋葱开始往外"回卷"。开头的 `i <= index` 是一个容易被忽略的保护：如果同一个中间件里调用了两次 `next`，`index` 已经前进过，这里会直接拒绝，因为重复执行后续链路几乎总是 bug。
>
> 中间件适合与具体路由无关的横切逻辑。如果某段逻辑只对少数几个接口生效，更合适的做法是使用路由级的守卫（见"路由守卫"一节），否则你就得在中间件里自己判断路径，这又回到了到处写条件分支的老问题。

这个版本先从一个具体的痛点讲起，再介绍概念；示例有出处；解释了示例中最关键的一行，并由此引出"注册顺序很重要"这个实用结论；实现部分把不长的 `dispatch` 整段贴出，逐一讲清了它的几个分支，并点出了一个不显眼但重要的细节；最后说明了什么时候不该用中间件。这就是每个功能讲解应该达到的样子。
