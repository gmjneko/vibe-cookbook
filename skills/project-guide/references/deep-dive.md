# 阶段三：功能深挖

这一阶段的目标是：用户读完以后，对这个功能的掌握程度接近它的维护者。能在各种场景下正确使用它，理解它内部每一个关键环节，知道它为什么被设计成这样，也知道如果要修改或扩展它应该从哪里下手。

## 定位功能

参数中给出的功能名可能是中文描述、英文标识符或者不完整的名字。先在 `_meta.md` 的功能清单中做模糊匹配，匹配不到再搜索源码。如果匹配到多个候选、无法确定用户指的是哪一个，列出候选并问用户，不要自行猜测。一次请求了多个功能时，每个功能写一个独立文件；如果这几个功能关系紧密，在各自文件中互相引用。

## 调查步骤

1. **完整阅读实现。** 从功能入口开始，沿调用链把所有相关代码读完，包括错误处理分支、边界条件、配置项如何影响行为。不要只读主路径。
2. **阅读测试。** 测试揭示了作者认为重要的行为和边界情况，也是最可靠的用法示例来源。
3. **阅读使用处。** 搜索项目内部对这个功能的调用，以及 `examples/` 中的用法。
4. **追溯历史。** 如果是 git 仓库，用 `git log --follow -- <文件>` 查看核心文件的演变，用 `git log -L <起始行>,<结束行>:<文件>` 或 `git blame` 查看关键代码段是什么时候、因为什么原因写成现在这样的。重点关注 commit message 中解释动机的内容、重构，以及修复 bug 的提交。如果 commit message 中引用了 issue 或 PR 编号，记下来作为依据。
5. **查找设计文档。** ADR、RFC、设计文档、代码中解释"为什么"的注释、CHANGELOG 中相关的条目。

## deep/<功能名>.md 的结构

各节的写作都要遵守 `style.md`，用连贯的段落讲解。篇幅不设上限，但每一段都应该提供新的信息。

### 1. 它要解决的问题

比阶段二更深入地讲清楚问题本身：这个问题难在哪里，朴素的解决方式会遇到什么麻烦。只有先理解问题的难点，读者才能理解后面的设计。

### 2. 完整用法

按由浅入深的顺序组织：

- 最基本的用法；
- 常用的配置和变体，每种变体对应什么场景；
- 进阶用法和与其他功能的组合；
- 不该使用它的场景，以及替代方案。

每种用法都配代码示例，说明适用场景，以及为什么在这个场景下要这样用。示例来源和验证要求同 SKILL.md 中的原则。

### 3. 实现细节

按执行顺序讲解完整的调用链，每一步说明：位于哪个文件的哪个函数、做了什么、为什么需要这一步、数据在这一步之后变成了什么样。调用链上的每个关键步骤都要贴出对应的代码，格式遵守 `style.md` 中的"代码摘录"：代码块写成 ` ```<语言> title="<文件名>" ` 的形式；代码不长就整段贴出，较长时才把与这一步无关的部分用注释省略，并且省略不能遮住任何影响执行过程的逻辑。不要只写"见 `tree.ts:134`"。

然后单独讲这几个方面（与该功能无关的可以略过）：

- **核心数据结构**：贴出它的定义（类型、类或结构体，省略无关字段），再讲字段含义，以及为什么选择这种结构；
- **边界情况与错误处理**：输入异常、资源不可用、并发冲突时会发生什么；
- **性能相关的设计**：缓存、懒加载、批处理等，以及它们为什么必要；
- **配置项如何影响行为**：每个关键配置在代码中的哪个位置生效。

配一张 mermaid 时序图或流程图，展示主要的执行过程。

### 4. 站在设计者的角度

这是本阶段最有价值、也最容易写成空话的一节。围绕下面这些具体问题来写，每个结论都要标明依据：来自 commit、issue、注释、文档的，写出来源；只是你根据代码做的分析，标注"（推测）"。

- 设计者面对这个问题时，有哪些可选方案？
- 为什么最终选择了现在这种方案？它相比其他方案好在哪里？
- 这个选择付出了什么代价，带来了哪些限制？
- 从 git 历史来看，这个功能经历过哪些重要的演变？每次演变是为了解决什么问题？
- 如果让你重新设计，现有方案在什么情况下会显得不够用？

不要为了显得深刻而列举一堆泛泛的设计原则（"体现了单一职责原则"之类）。只有当某个原则能具体解释这段代码中的某个决定时，才值得提出来。

### 5. 常见的坑

新手容易犯的错误和容易误解的行为，每一条都要说明会产生什么后果、为什么会这样（追溯到代码层面），以及正确的做法。依据来自测试用例、issue、文档中的警告，或者代码中显而易见的陷阱。

### 6. 如果你要修改或扩展它

想改变它的行为应该改哪里；项目是否提供了不改源码就能扩展的方式；修改后需要运行哪些测试；有哪些不明显的依赖关系，改动时容易牵一发而动全身。

### 7. 相关功能

列出与它紧密相关的其他功能，并用一句话说明关系，方便读者继续深入。如果这些功能还没有深挖过，提示可以用 `/project-guide deep <功能名>` 继续。

写完后更新 `_meta.md` 中功能清单的"已深挖"一列。
