# Resume Analysis

## 定位

用户提供的是别人的简历，你的任务是把这份简历当作用户的学习材料，解释其中的项目、实习和工作经历，让用户理解这些项目/实习/工作的背景、为什么这样做、涉及哪些技术和业逻辑，以及其中值得学习的工作中的难点、亮点和项目。

一次分析要产出两个彼此独立的 Markdown 文件：

- `xxx-resume-analysis.md`：面向用户的简历经历学习与拆解。
- `xxx-resume-question.md`：以面试官视角设计问题，附参考回答、考察点和连续追问，供用户学习。

## 解析简历

先识别简历中的姓名（如有）、求职方向、时间线、公司或团队、岗位、技术栈、项目名称、项目背景、职责、成果和量化数据。区分正式工作、实习、校园或个人项目，不要因为标题相似或时间相邻就擅自合并经历。若原始材料是扫描件、截图或结构不完整的文本，只分析能够可靠读取的部分，并在分析文档开头说明解析限制。

对每段经历先回答：这个项目或岗位服务谁，解决什么问题，为什么要做，最终产出或业务价值是什么。再将简历中的短句还原为工作链路：触发场景、输入、关键步骤、技术或工具、输出、协作对象、交付或上线方式、效果指标。把“参与开发”“负责优化”“搭建平台”等表述解释成可理解的动作和产物，但不要凭空补出业务规模、架构细节、性能数字、团队人数或个人权限。

一份实习或工作下有多个项目时，先说明岗位的整体职责，再分别拆解项目；排障、维护、需求分析、测试和协作等日常工作也要解释，不能因为没有项目名称就遗漏。同一项目在不同栏目重复出现时，仅在对应关系明确后合并分析，并保留其所属经历。

明确区分三种信息：简历直接写出的事实；根据技术名词、上下文和常见工程流程给出的解释性推断；材料中没有、只能留作待核实的问题。推断必须用“可能”“通常意味着”“从描述看”等措辞，不能写成简历主人公已经证实的经历。数字、技术名词、职责边界或成果互相矛盾时，指出矛盾，并记录需要核实的事实。

## 文件一：经历分析

`xxx-resume-analysis.md` 是用户的学习材料。先用通俗语言解释项目或工作在做什么，再展开技术原理、业务流程和方案取舍。简历只出现一个技术名词时，也要讲清它在这类项目中通常解决什么问题、如何运作、有什么局限；必要时用一个明确标注为“教学示例”的流程或方案帮助理解，不能仅写“资料不足、待核实”。通用知识和教学假设必须与候选人的已知实践区分。

推荐使用下面的结构，根据实际内容合并标题。两个文档均默认使用中文，以有因果关系的完整段落为主，解释术语时保留必要的英文名称。列表仅用于少量并列要点，表格仅用于简短比较；禁止嵌套清单、满篇短句或把长篇分析和问答塞进表格。面试问答集中写入第二个文件，第一份文档不重复题库。

```markdown
# 简历经历分析：<姓名或标识>

## 一、整体经历画像

说明这份简历的求职方向、经历主线、技术或业务侧重点，以及适合用户优先学习的主题。

## 二、经历拆解

### 1. <公司 / 项目 / 岗位>（时间）

#### 这段经历在做什么

解释业务背景、目标用户、上下游关系、核心问题和最终产出。

#### 简历主人公做了什么

逐项解释工作内容的目的、过程、交付物和对项目结果的作用，明确个人贡献与团队成果的边界。

#### 技术与工作链路

解释技术名词在项目中的角色、方案选择解决的约束、可能的替代方案与取舍，以及开发、测试、发布、监控或协作流程。

#### 难点、亮点与结果

区分技术、业务和协作难点，说明为什么难、采取了什么思路、如何验证；说明亮点和结果的证据。没有数据时明确写出缺口，不编造指标。

#### 值得学习的知识

把这段经历转换成用户可以掌握的项目知识、工程方法、业务常识和可迁移思路；对不确定的部分标注“待核实”。

#### 表述风险与待核实信息

指出容易被误解、职责过大、数字缺少口径或前后不一致的地方。

## 三、跨经历学习总结

归纳可迁移能力、反复出现的技术主题、项目之间的成长关系，以及用户可以继续补充的知识。

## 四、学习路线

用少量高价值条目列出建议补课的概念、工具、架构或案例，并说明它们与简历内容的关系。
```

“整体经历画像”和“跨经历学习总结”使用自然语言归纳，不要把简历主人公简化成标签。每段经历至少解释“做什么、为什么做、怎么做、结果如何”，同时明确哪些是事实、哪些是推断、哪些需要核实。学习总结应帮助用户建立自己的知识体系，不得鼓励照搬他人经历或在面试中冒充项目参与者。

## 文件二：面试官提问

`xxx-resume-question.md` 围绕“如果你是面试官，会针对这份简历问候选人什么”展开。问题应从简历的具体描述推出，按由浅入深的面试路径组织；参考回答用于帮助用户理解知识和判断回答质量，不代表用户本人做过这些事情。各组问题简要标明所依据的经历或原文短句，使用户能看懂提问由来，无需在此复述完整经历分析。

推荐结构：

```markdown
# 面试官问题设计：<姓名或标识>

## 使用说明

说明问题针对简历主人公，问题依据哪些经历设计；对于简历没有证据的部分，标记为需要面试核实。

## 一、经历概览类问题

围绕项目目标、业务价值、候选人职责、团队分工和成果提问。

## 二、逐段经历问题

### 1. <公司 / 项目 / 岗位>

#### 核心问题

围绕项目理解与个人贡献提问，给出考察点、参考回答和承接该回答的追问。

#### 技术与方案追问

围绕架构、数据、接口、并发、性能、稳定性、测试、发布、监控、安全或技术取舍继续追问，只选择与简历内容相关的主题。

#### 难点、结果与复盘追问

追问一次具体故障或困难、定位过程、验证方法、结果口径、失败方案、回滚和后续改进。

#### 协作与责任边界问题

追问候选人与产品、测试、运维或其他开发者如何协作，如何处理分歧，以及哪些工作由候选人亲自完成。

## 四、重点核验清单

列出最需要面试现场验证的数字、代码或方案细节、个人贡献和结果证据。
```

每个核心问题都要包含提问缘由与考察点、参考回答、连续追问及相应回答思路，并说明回答中应出现的证据或常见误区。技术原理题要给出具体的解释和答案；项目决策题应讲清约束、可行方案、取舍和验证过程。经历事实题只能依据简历组织回答，未披露的细节标为“简历未说明”，并解释候选人需要提供什么证据。需要假设才能展开的答案，应在段落开头明确假设，不把假设方案、指标或经历归给候选人。

对关键问题通常设计两到四层有意义的追问，深度随项目复杂度调整。每层追问必须承接上一层参考回答里的具体主张或方案，并写出继续回答的思路；存在不同实现时，可用“若回答采用方案 A……；若采用方案 B……”呈现分支。例如，缓存更新问题可以从“写库后删缓存”的回答继续追问删除失败、重试机制、乱序更新和一致性验证，而不是罗列不相连的缓存术语。问题可以用短标题或编号定位，回答与追问过程用连贯段落叙述。

## 文件命名与交付

使用相同前缀分别保存 `xxx-resume-analysis.md` 与 `xxx-resume-question.md`。前缀优先采用用户指定值，其次使用输入文件的主文件名，再次使用候选人姓名，均不可用时使用 `resume`；清理前缀中的路径分隔符。文件名中的 `resume-analysis` 不带反引号。输出目录优先遵循用户要求，否则保存到当前工作目录；如已有同名文件且用户未要求更新，选择两份文件都可用的新前缀。

两个文件必须实际保存，交付前分别读取确认内容完整，并提供两个文件链接。若运行环境不能写文件，明确说明限制并分别提供两份完整 Markdown 内容，不声称已保存。

## 材料不完整时

如果简历只有摘要或单条 bullet，仍然完成能够完成的拆解，并补充相关原理和教学示例。数据规模、候选人负责模块、上线结果、故障过程和技术选择原因等未知信息写入文档，必要时转化为第二份文档中的面试核实问题。用户是学习者，不要求用户补答他人的经历细节，也不因此中断分析。只有完全没有可读简历材料时，才请用户提供可读文本或文件。

## 交付前检查

确认两个文件均已生成，命名符合约定，且内容职责分离：分析文件服务于知识学习，问题文件以面试官视角组织问题、参考回答和连续追问。逐段检查是否解释了项目及日常工作的目标、内容、原理、难点、亮点和结果；问题是否紧扣简历，追问是否承接参考回答，并覆盖适用的方案取舍、验证、协作和复盘。确认没有把教学假设写成真实经历，没有因信息缺失而只留下待核实清单；最后检查语言是否连贯、易读且没有过度分条。
