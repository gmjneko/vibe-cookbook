# Resume Analysis

## 这个 skill 要解决什么问题

用户手里拿到的是别人的简历——可能来自学长、同学，也可能是网上流传的优秀简历。简历为了压缩篇幅，会把几个月的工作浓缩成"基于 Redis 分布式锁解决库存超卖，接口 QPS 提升 3 倍"这样一行字。用户认得每个词，却不知道这行字背后是什么场景、当时遇到了什么问题、方案内部怎么运作、为什么选它而不是别的。这个 skill 的工作就是把这些被压缩掉的信息还原出来，让用户借别人的经历补齐自己的项目知识和面试知识。

产出分成两份互相独立的文档。`xxx-resume-analysis.md` 是学习笔记，回答"这段经历到底在做什么、背后的原理是什么"；`xxx-resume-question.md` 是面试官视角的题库，回答"面试官看到这份简历会怎么问、好的回答长什么样、追问会往哪里走"。之所以分开，是因为两者的使用时机不同：前者用来系统学习，后者用来自测和模拟面试，混在一起会让两种用途都变得难用。

## 写作风格：每个要点都是一个完整的小故事

这两份文档最常见的失败写法，是把简历里的 bullet 换个说法再列一遍——"使用 Kafka 进行异步解耦""引入缓存提升性能"。这种功能清单只是复述了简历，用户读完仍然不知道为什么要这样做，也就没有学到任何东西。

正确的写法是让每个要点都覆盖三个层次，并用有因果关系的段落串起来。

**场景**：这件事发生在什么业务情境下，遇到了什么具体问题或约束。例如"秒杀开始的一瞬间，几万个请求同时扣减同一件商品的库存，数据库行锁成为瓶颈，还出现了超卖"。场景让用户知道这个技术点为什么会出现，而不是凭空冒出一个名词。

**解释**：简历主人公（或这类项目通常）具体做了什么，做完之后系统的行为发生了什么变化。"负责优化""参与搭建"这类模糊动词要还原成能看懂的动作和产物。

**原理**：方案为什么能解决问题——内部如何运作、依赖什么前提、有什么局限、常见的替代方案是什么以及为什么没选。这是用户真正能带走的知识，也是面试官追问的落点。

三层不必每次都用小标题机械地切开，写成一两段连贯的文字往往更自然；判断标准是读完一个要点后，用户能说清"在什么情况下、做了什么、为什么有效"。列表只用于少量真正并列的内容（例如几个候选方案的名字），表格只用于简短的横向比较。不要嵌套清单，也不要把长篇分析或问答塞进表格，因为表格单元格会把因果链切碎。

两份文档默认使用中文，技术术语首次出现时保留英文名称，例如"消息队列（Message Queue）"，方便用户之后检索资料。

## 第一步：读懂简历

先通读全文，识别求职方向、时间线、每段经历的公司或团队、岗位、项目名、技术栈、职责描述和量化结果。正式工作、实习、校园项目和个人项目要区分开，它们的可信边界不同，面试官的关注点也不同；不要因为标题相似或时间相邻就合并两段经历。同一个项目在不同栏目重复出现时，只有在对应关系明确后才合并，并保留它所属的经历。

如果材料是扫描件、截图或排版错乱的文本，只分析能可靠读出的部分，并在分析文档开头说明哪些内容没有识别出来，避免用户误以为看到的就是简历全貌。

简历里通常有手机号、邮箱、住址等个人信息。文档中用姓名或一个代称指代简历主人公即可，不要转录联系方式——这些信息对学习没有帮助，却会随着笔记被传播。

## 区分事实、推断与教学示例

还原简历必然要补充大量简历没写的内容，这正是这个 skill 的价值所在，也是最容易出错的地方。补充的内容分三种，写作时要让用户一眼能分辨。

简历原文直接写出的是**事实**，可以直接陈述。根据技术名词、上下文和常见工程实践得出的是**推断**，要用"从描述看""通常意味着""这类项目一般会"等措辞引出，不能写成简历主人公已经证实的经历。为了讲清原理而构造的流程或方案是**教学示例**，要明确标注，例如"下面用一个典型的库存扣减流程来说明（教学示例，非简历内容）"。

之所以要这样区分，是因为用户最终要在自己的面试里使用这些知识。如果推断被写成事实，用户会把某种实现误当成唯一的标准答案；如果分不清哪些是别人的经历，用户可能在面试中不自觉地照搬，把他人的项目说成自己的。这个 skill 的目标是帮用户建立自己的知识体系，而不是提供一套可以冒用的经历。

对于简历没写、也无法合理推断的信息——数据规模、团队人数、个人负责的模块边界、结果数据的统计口径——不要编造，直接说明缺失，并在第二份文档里转化为面试官会核实的问题。但信息缺失不是停止讲解的理由：简历只出现一个技术名词时，依然要讲清它在这类项目中通常解决什么问题、怎么运作、有什么局限，只写一句"资料不足，待核实"对用户毫无帮助。如果数字、职责或技术描述前后矛盾（例如"独立负责"和"协助完成"指向同一模块），要指出矛盾，并说明面试中可能被如何追问。

## 文件一：经历分析

`xxx-resume-analysis.md` 的读者是想学习的用户。参考结构如下，可以根据实际内容合并或省略小节：

```markdown
# 简历经历分析：<姓名或代称>

## 一、整体画像

用一两段话说明这份简历的求职方向、经历主线和技术侧重，以及最值得用户优先学习的是哪几段经历、为什么。

## 二、经历拆解

### 1. <公司 / 项目>｜<岗位>（时间）

#### 背景：这段经历在做什么

业务是什么、服务谁、上下游是谁、要解决的核心问题和最终产出。如果一段实习下有多个项目，先讲岗位的整体职责，再分项目展开。

#### 要点 1：<一句话概括，如"用 Redis 分布式锁防止库存超卖">

> 简历原文：<引用对应的描述>

依次讲清场景、解释和原理（见"写作风格"一节），再说明难点在哪、有哪些替代方案及取舍、结果数据该如何理解（口径是否清楚、个人贡献与团队成果的边界在哪）。不确定之处就地标注为推断或待核实。

#### 要点 2：……

#### 边界与疑点

职责是否写得过大、数字是否缺少口径、描述之间是否矛盾，以及面试时这些地方可能被如何质疑。

## 三、跨经历总结

这些经历之间有什么成长线索，哪些技术主题反复出现，体现了哪些可迁移的工程能力。用自然语言归纳，不要把人简化成几个标签。

## 四、学习路线

挑少量高价值的概念、工具或案例，说明每一项对应简历中的哪个要点、学到什么程度才算够用。
```

"要点"是这份文档的核心单位。一个要点通常对应简历里的一句或一组描述，但划分标准是"能否讲成一个完整的场景—解释—原理故事"：一句话里塞了三个互不相关的技术，就拆开讲；几句话说的是同一件事，就合起来讲。排障、维护、需求分析、测试、跨团队协作这类没有项目名的日常工作也要作为要点讲解，它们往往最能体现真实的工作经验，面试官也常从这里切入。

篇幅跟着学习价值走：技术含量高、面试必被追问的要点写透，常规的配置或增删改查一段带过即可。面试问答集中放在第二份文档，这份不重复题库。

## 文件二：面试官提问

`xxx-resume-question.md` 模拟一位拿到这份简历的面试官会怎么问。问题必须从简历的具体描述推导出来，按由浅入深的面试路径组织：先确认候选人理解项目，再深挖技术方案，最后验证个人贡献和复盘能力。参考回答是帮助用户理解知识、判断回答好坏的范例，不代表用户本人做过这些事。

```markdown
# 面试官问题设计：<姓名或代称>

## 使用说明

说明这些问题依据哪些经历设计，参考回答中哪些部分基于简历、哪些是假设展开，以及建议的用法（例如先遮住参考回答自己作答，再对照）。

## 一、开场与整体问题

围绕整体经历、求职方向和最有代表性的项目提问。

## 二、逐段经历深挖

### 1. <公司 / 项目>

#### Q1：<问题>

**为什么问**：……

**参考回答**：……

**追问链**：……

#### Q2：……

## 三、重点核验清单

汇总最需要在面试现场核实的数字、方案细节、个人贡献边界和结果证据，并说明每一项可以用什么问题去验证。
```

每道核心题按"为什么问—参考回答—追问链"展开，三部分都写成连贯段落，和分析文档的场景—解释—原理一一呼应。

"为什么问"对应场景：说清面试官是被简历的哪句话触发了这个疑问，想考察的是原理理解、方案判断，还是个人贡献的真实性。用户由此学会从简历反推面试官的关注点，而不只是背题。

"参考回答"对应解释和原理。技术原理题要给出具体、正确的答案；方案决策题要讲清约束、候选方案、取舍理由和验证方式；经历事实题只能依据简历组织回答，简历没写的细节标为"简历未说明"，并说明候选人此时需要拿出什么证据。需要假设才能展开的回答，在段落开头写明假设。最后点出好回答应当包含的证据，以及常见的失分点。

"追问链"是这份文档区别于普通题库的地方。真实面试的追问总是抓住上一句回答里的某个具体说法往下挖，所以每一层追问都必须承接上一层参考回答中的主张，并写出继续回答的思路。例如上一层回答"写库之后删除缓存"，下一层就问"删除失败怎么办"；回答提到重试，再问"重试期间读到旧值、或两次更新乱序怎么办"；最后问"你怎么证明线上确实一致"。这样的链条才能逼近候选人的真实理解深度，而在缓存话题下罗列一串互不相关的术语做不到这一点。关键问题通常设计两到四层追问，深度随项目复杂度调整；回答存在不同路线时，可以写成"如果回答采用方案 A……；如果采用方案 B……"的分支。

覆盖面跟着简历走：架构、数据、并发、性能、稳定性、测试、发布、监控、安全、协作分工都是可选主题，只挑与简历内容相关的，不要为了凑齐维度而硬问。

## 文件命名与保存

两份文件使用相同前缀。前缀依次取：用户指定的名字、输入文件的主文件名、简历主人公的姓名，都没有时用 `resume`；去掉路径分隔符、空格等不适合出现在文件名里的字符。最终文件名是纯文本，例如 zhangsan-resume-analysis.md，不要把 Markdown 的反引号带进文件名。

保存位置优先遵循用户要求，否则放在当前工作目录。如果已存在同名文件且用户没有要求覆盖，换一个两份文件都不冲突的前缀（例如追加日期），避免覆盖用户之前的笔记。

## 交付

两份文件写完后各读一遍，确认内容完整、没有被截断，然后告诉用户两个文件的路径，并用两三句话说明这份简历最值得学的是什么。如果运行环境不能写文件，说明限制并直接给出两份完整的 Markdown 内容，不要声称已经保存。

只有在完全没有可读的简历内容时才向用户索要材料。简历只有寥寥几行时，依然完成能完成的拆解，用原理讲解和教学示例补足。不要让用户去补充别人经历里的细节——用户是学习者，并不掌握这些答案。

交付前回头检查：每个要点是否讲清了场景、做法和原理，而不是在换句话复述简历；推断和教学示例是否都有标注，没有被写成简历主人公的真实经历；追问是否一层层承接上一层的回答；两份文档是否各司其职、没有互相重复。
