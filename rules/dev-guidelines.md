## 通用开发规范

本规范面向开发期的项目，目标是在保持迭代速度的同时，不在早期留下技术债。但**快速不等于临时**：早期的补丁会被后续代码依赖，越晚清理代价越高，所以每次改动都按“这就是最终形态”的标准完成；开发期没有历史包袱，可以直接选择最清晰的设计。

### 项目画像

各项目在项目级 CLAUDE.md / AGENTS.md 中填写以下信息。下文规则优先按画像执行；画像缺失且本次改动涉及该项时才询问用户，未涉及则不询问。

```markdown
### 项目画像
- 阶段：快速开发期（默认）/ 已上线 / 维护期
- 部署形态：本地工具 / 内网服务 / 公网服务
- 兼容性：无兼容要求（默认）/ 需兼容 xxx
- 数据：开发数据可重建（默认）/ 需保留 xxx
- 安全级别：基础（默认）/ 生产级
- 验证命令：如 `pnpm test`、`pnpm lint`、`pnpm typecheck`
- 提交风格：Conventional Commits，description 使用英文（默认）/ 中文
```

### 红线

以下行为任何情况下都**不做**，无需权衡：

- 为了让测试通过而修改、跳过、删除测试，削弱断言，或硬编码期望值。认为测试本身有误时，先说明理由，经用户同意再改。
- 静默吞掉异常，或用默认值、空结果伪装成功（见「错误处理」）。
- 未经确认执行不可逆操作：清库删表、重建数据、读写/修改 `.env` 等密钥配置，以及任何针对生产环境的操作。如果开发中涉及到数据库的修改，某张表已经确认废弃或者旧数据已不再可用，那应先明确向用户说明后再进行修改。
- 未经确认执行 git 提交。
- 在代码、日志或提交中写入密钥、token 等凭据。
- 声称执行过实际没有执行的检查。

### 正确实现优先

- 动手前先读相关代码：定位根因，理清职责边界，找到现有架构中合适的位置和抽象。新写工具函数或模块前，先搜索仓库中是否已有可复用的实现，如果可复用的实现所在模块合适则优先复用；若有可复用的实现，但可复用的实现的位置不在通用模块或者是与本模块相关的模块，直接使用可能会导致模块间耦合或者是依赖关系混乱等情况，则应先进行合理抽象再进行复用。
- 让实现自然地属于整个系统，而不是让当前场景暂时可用。除非`正确实现会显著增加工程量`或`修改面过大`，否则尽可能不使用局部特判、绕过分层、临时适配器或复制已有逻辑来掩盖结构问题，也不要留下“以后再整理”的代码。
- 为修复根因或正确实现功能所必需的重构、多模块修改、数据模型或接口调整，属于本任务范围，应一并完成。如果这会显著扩大任务范围，先说明根因、完整方案、影响范围和成本，由用户决定；不要自行退回临时补丁。
- 与本任务无关、只是“顺手可以更好”的改进，在最终说明中提出建议，不动手。
- 除非用户明确要求，否则实现应该保持简单：在不需要特判、不绕过分层就能满足需求的方案中，选最简单的那个。
- 使用不熟悉的库、框架或接口前，先查源码、类型定义或文档确认签名和版本行为，不凭记忆编造 API。如果用户没有提供对应的库的文档或者是源码，你应该先自行进行搜索，如果搜索无果，则向用户询问相关文档的链接，不得擅自解压依赖包（例如 Java 的 jar 包）去查看源码。能方便查看依赖源码的场景除外，例如node_models。
- 引入新依赖前先确认，优先使用标准库和项目已有依赖。
- 用户给出的设计明显不合理，或存在明显更合适的方案时，先说明问题和建议方案，由用户决定。

### 决策与询问

决策按影响分两级：

- **高影响决策**：涉及数据模型、公开接口或契约、安全语义、跨模块架构、主要用户流程、不可逆操作，或多个可行方案的长期维护成本差异明显。暂停并询问，不替用户选择。
- **低影响决策**：内部命名、局部实现方式、私有函数拆分等可逆细节。按合理默认值直接实现，在最终说明里用一句话交代选择和理由，方便用户调整。

能从现有代码、文档或项目画像推出的细节不属于待决策问题，直接按既有约束执行。

询问高影响决策时：

- 先完成必要的代码、配置、文档和数据结构调查，不问自己能查到的问题。
- 同一任务中的问题尽量合并为一次提问。
- 说明需要决定的问题、已知约束、各方案的优缺点与成本、影响范围，以及推荐方案和理由。
- 用户决定后再继续。重要的架构决定写入项目已有的 ADR 或架构文档；项目没有此类文档时，在最终说明中提示用户是否需要记录。

### 错误处理

默认 fail-fast 而不是 fallback：输入、状态、协议、配置或数据不符合预期时，立即返回明确错误。开发期最大的风险不是程序崩溃，而是错误被掩盖后带着错误状态继续运行，最后在远离根因的地方暴露。

- 不要静默吞掉异常。空 `catch`、只打日志后继续执行、把异常转换成 `null`/`undefined`/空集合/空对象或虚假的成功结果，都属于此类。日志不是错误处理。
- 不要捕获当前层无法真正处理的异常。让它传播到明确的系统边界，在那里统一转换为 HTTP/RPC 错误、任务失败、非零退出码、界面失败状态或告警。
- `try/catch` 只用于以下情况：
  1. 当前层能执行明确设计过的恢复操作；
  2. 把底层异常转换为本层契约中的结构化错误，并保留原始 `cause`；
  3. 补充有助于定位问题的上下文后重新抛出；
  4. 资源清理（优先用 `finally`）。
- 捕获后不得继续执行依赖该操作成功的逻辑。恢复操作必须保证状态仍然有效，否则终止当前操作。
- 解析配置、消息、文件或持久化数据失败时，暴露数据错误，不要自动忽略字段、重置数据或回退到默认配置。
- Fallback 会改变可观察行为，属于产品或架构决策，未经用户确认不要添加。经确认添加的恢复逻辑或 fallback，需要用测试覆盖其触发条件和恢复后的行为。
- 发现已有 fallback 掩盖了根因时，删除它，让错误在正确的边界暴露，并补充回归测试。

> fail-fast 不等于让整个程序崩溃，而是让错误到达合适的边界并明确失败，不假装成功。

### Bug 修复与失败尝试清理

- 修复根因而不是症状，并补充能防止回归的测试（纯样式和布局问题除外）。
- 一个 bug 有可能有多种修复方式，选择最符合项目整体设计的修复方式，详见 @正确实现优先 章节。
- 开始修复前先查看工作区状态（`git status` / `git diff`），区分已有改动和本次改动。需要多次尝试时，记录每次尝试修改了哪些位置。
- 如果一个 bug 修复历经多次修改才成功修复，确认最终方案有效后，回溯本次修复期间的全部改动，逐项判断是否属于根因修复、回归测试或必要重构：必要的保留，其余删除。重点清理失败尝试留下的临时判断、额外状态、调试日志、依赖，以及只为旧尝试服务的测试。
- 只清理本次修复引入的改动，不动用户原有或其他任务的改动；无法确定归属时询问。
- 清理后重新运行回归测试，确认问题仍然被修复。

### 破坏性变更

快速开发期默认允许破坏性变更（项目画像另有声明时除外）。这是避免技术债的关键：没有外部用户时，保留旧形态只会制造负担。

- 优先选择最清晰、最接近最终形态的设计，不为兼容旧实现而妥协。
- 发生破坏性变更时，同步更新所有调用方、接口契约、schema、测试、配置和文档，并删除被替代的代码。不要留下兼容别名、双写、已废弃但未删除的函数或被注释掉的旧代码。
- 开发数据可以重建，不要为保留开发快照而扭曲目标数据模型。但实际删除或重建数据前，先说明影响并确认（见「红线」）。
- 项目画像声明了兼容要求，或项目已对外发布时，遵守相应约束，设计迁移、版本协商或弃用周期。
- “无需兼容旧实现”不等于可以跳过用户要求的能力、安全约束或明确规定的迁移规则。

### 安全

安全设计级别跟随项目画像。

- **基础级**（默认，适用于本地工具、离线项目、开发期内部项目）：守住底线，不为安全单独选择明显增加复杂度的方案。底线包括：
  - 密钥和凭据只放在环境变量或被 git 忽略的文件中，不硬编码、不提交、不打印到日志；
  - 数据库查询参数化，不拼接 SQL；优先使用成熟的 ORM 框架。
  - 不对外部输入使用 `eval`，不拼接 shell 命令；
  - 在系统边界校验外部输入；
  - 本地服务默认只监听本机地址，确有需要时再对外开放。
- **生产级**（公网服务、处理他人数据）：把安全作为架构和方案设计的一部分，覆盖认证授权、输入校验、数据保护、依赖风险等方面。

### 验证与完成标准

- 先运行与改动最相关的检查，再运行受影响范围的完整检查。按项目类型选用：单元/集成测试、类型检查、lint、格式化检查、schema 或迁移验证、必要的安全检查。
- 只写必要且有价值的测试：覆盖核心逻辑、边界条件和本次修复的回归场景，不为每个细节堆砌重复用例。难以构造的测试可以不写，但要在最终说明中指出哪些部分需要用户自行验证。
- 纯视觉改动不要求功能测试。有条件时用浏览器自动化截图自验，否则请用户人工确认。
- 检查全部通过，或已明确说明失败原因、影响和后续处理，才算完成。
- 最终说明包括：改了什么；实际执行了哪些检查及结果；未执行或失败的检查及原因；低影响决策的选择；发现但未处理的问题。

### 代码风格与变更范围

- 沿用项目现有的代码风格、目录结构、依赖管理、构建工具和测试框架，不在同一项目中引入平行的实现方式。
- 文档和注释遵循项目既有语言；没有约定时使用用户所用的语言。标识符、配置键和公开接口使用清晰一致的英文命名。
- 注释解释“为什么”，不复述代码在做什么。不保留被注释掉的代码。
- 修改范围限于本任务，不覆盖工作区中与任务无关的已有改动。
- 修改配置、依赖、构建脚本或部署文件时，评估对本地开发、测试和运行环境的影响，并在最终说明中提及。
- 每个独立功能或 Bug 修复形成可独立审查、验证和回滚的变更单元。

### 提交

- 完成一个独立且已验证的变更后，主动建议提交，等用户确认后再执行。建议时简要说明主要变更、验证结果和已知限制。
- 用户追加了与当前功能无关的修改时，先确认合入同一提交还是分开提交。
- 提交信息遵循项目画像或仓库已有风格；两者都没有时使用 Conventional Commits：`type(scope)!: description`。
  - `type`：`feat`、`fix`、`refactor`、`perf`、`style`、`docs`、`test`、`build`、`ci`、`chore`、`revert`。
  - `scope`：受影响模块的小写名称，多个模块用逗号分隔；无法确定或项目只有一个模块时省略。
  - `!`：仅用于破坏性变更，并在正文中用 `BREAKING CHANGE:` 说明影响。
  - `description`：简洁说明做了什么，不描述实现过程；英文时使用小写开头。
  - 示例：`feat(desktop): skeleton loaders for list/message loading states`
