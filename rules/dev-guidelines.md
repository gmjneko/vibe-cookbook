## 通用开发规范

### 正确实现优先

- 开发新功能或修改现有模块时，先定位根因、职责边界和现有架构中的合适抽象，再按当前已知的最佳方案完整实现。目标是让实现自然地属于整体系统，而不是只让当前场景暂时可用。
- 除非用户或架构明确要求，尽量不要使用局部特判、绕过分层、临时适配器等方式掩盖结构问题。不要留下“以后再整理”的补丁，因为后续代码通常会继续依赖它们，形成补丁套补丁。
- 如果正确方案需要同时修改多个模块、数据模型、接口契约等，应在任务允许的范围内将其完成，如不确定业务范围，应该向用户提问。如果正确方案改动会显著扩大任务范围，先向用户说明根因、完整方案、影响范围和成本，并请求决定，不得自行退而采用临时补丁。
- 方案的选择应该保持简单，只有在相对简单的方案无法**优雅地**实现需求的时候才应该考虑更为复杂的方案。
- 如果用户给出的设计明显不合理，或当前架构中存在明显更合适的方案，应先说明问题、建议方案、影响和成本，再请求用户决定。

### Bug 修复与失败尝试清理

- 修复 Bug 时应修复产生问题的根因，并补充能够防止回归的测试（除非是难以进行编写测试用例的前端、客户端等视觉修改）。
- 如果一个 Bug 经历了多次尝试才最终修复，在确认最终方案有效后，应回溯检查本次 Bug 前几次尝试引入的全部修改。判断它是否属于根因修复、回归测试或必要重构的一部分：必要的保留，不必要的删除。
- 重点清理失败尝试留下的临时判断、额外状态、日志、依赖，以及只为旧尝试服务的测试。
- 清理范围只包括为本次 Bug 修复引入的修改，不得误删用户原有或其他任务的改动。若无法确定某项修改的归属或必要性，按“不确定决策必须询问”的规则请求用户确认。
- 清理完成后重新运行回归测试，确认移除无关修改后问题仍然得到修复。

### 安全边界

- 要分清这是一个什么样的项目，根据项目性质的不同选择不同的安全设计级别。
- 如果此项目的需要上线，安全性很重要，那么应该完整考虑安全性问题，并且将安全性作为架构/方案设计的一部分。
- 如果此项目只是用户的小工具、离线项目，则应该只考虑基本的安全问题，不要按照**竞态**级别去设计安全边界，不需要单独为了安全性而去选择会**明显增加**项目复杂度以及开发难度的方案。

### 兼容性与破坏性变更

- 是否需要兼容旧 API、旧协议、旧配置、旧数据库或已有数据，必须根据项目阶段、发布状态和用户要求明确判断，不得默认假设。并且兼容性问题应该在你进行计划或修改**之前**就应该向用户确定。
- 如果项目明确处于开发或重构阶段，且用户明确没有兼容性要求，可以进行破坏性变更，并优先选择更清晰、最终形态更合理的设计。
- 如果项目已经对外发布，或用户没有明确允许破坏性变更，则必须遵守相应的兼容性约束，并设计必要的迁移、版本协商、弃用周期或兼容层。
- 发生允许的破坏性变更时，应同步更新所有调用方、接口契约、schema、测试、配置和文档，并删除被替代的代码。不要增加没有明确需求支持的兼容别名、双写或一次性迁移。
- 在用户**明确允许破坏性变更**的前提下，开发过程中的数据可以重建，但必须提前向用户说明影响并确认。不要为了保留开发快照而扭曲目标数据模型。
- “无需兼容历史实现”不等于可以跳过用户要求的能力，也不代表可以忽略产品明确要求的版本协商、安全约束或数据迁移规则。

### 不确定决策必须询问

- 只要对正确方向存在实质不确定性，或者多个可行方案会在架构、数据模型、安全语义、用户体验或长期维护成本上产生不同结果，就必须暂停实现并询问用户，不得擅自替用户选择。
- 提问前先完成必要的代码、配置、文档、ADR和数据结构调查。
- 询问时必须说明：
  - 需要决定的问题；
  - 已知约束；
  - 每个可行方案的优势；
  - 每个方案的潜在问题和成本；
  - 影响范围；
  - 推荐方案及推荐理由。
- 用户作出决定后再继续实现，并在需要时把决定写入 ADR、架构文档或重构计划。
- 能由现有文档或代码边界明确推出的实现细节，不属于不确定决策，应直接按既有约束执行。
- 如果现有约束与目标功能冲突、需要补全系统能力，或会违反“正确实现优先”原则，应先询问用户再继续实现。

### 错误处理与失败策略

- 默认采用 fail-fast。输入、状态、协议、配置或数据不符合预期时，应立即返回明确错误，不得用默认值、空结果或替代路径伪装成功。
- 禁止静默吞掉异常，包括空 `catch`、只打印日志后继续执行、把异常转换为 `null`、`undefined`、空集合、空对象或虚假的成功结果。
- 除非是必要的，否则不要为了“提高健壮性”加入未经用户或架构确认的 fallback。Fallback 会改变可观察行为，需要被视为明确的产品或架构决策。
- 不要捕获无法在当前层真正处理的异常。不能恢复时，应让异常继续向上传播，由明确的系统边界统一转换为 HTTP/RPC 错误、消息响应、任务失败、用户可见错误、监控告警或进程失败。
- `try/catch` 仅允许用于以下情况：
  1. 当前层能够执行明确且经过设计的恢复操作；
  2. 将底层异常转换为该层公开契约中的结构化错误，同时保留原始 `cause`；
  3. 补充对定位问题有价值的上下文后重新抛出；
  4. 执行资源清理；仅清理时优先使用 `finally`。
- 捕获异常后不得继续执行依赖该操作成功的后续逻辑。恢复操作必须能够证明状态仍然有效，否则应终止当前操作。
- 解析配置、消息、文件格式和持久化状态失败时，默认暴露数据错误，不得自动忽略字段、重置数据或回退到默认配置，除非相应规范明确要求。
- 日志不是错误处理。`catch` 中记录日志后仍须重新抛出、返回明确失败，或执行已经定义的恢复方案。
- 新增异常捕获或 fallback 时，必须通过测试覆盖正常路径、失败路径和恢复路径，并说明为什么当前层能够安全恢复。
- 修复 Bug 时，如果发现原有 fallback 掩盖了根因，应删除该 fallback，让错误在正确边界显式暴露，并补充回归测试。

> 这并不要求所有错误都导致整个程序崩溃。正确做法是让错误传播到合适的边界，例如接口返回结构化错误、任务标记为失败、命令返回非零退出码、界面显示失败状态或服务触发告警。关键是明确失败，而不是假装成功。

### 验证与完成标准

- 根据改动范围先运行最小相关检查，再运行受影响层级的完整检查。
- 根据项目类型和改动内容选择适用的验证方式，可选：
  - 单元测试、集成测试（除非是视觉修改）；
  - 类型检查、静态分析和 lint；
  - 格式化检查；
  - 数据库 schema 或迁移验证；
  - **必要的**安全检查；
- 仅在检查通过，或已明确记录失败原因、影响范围和后续处理方式后，才视为任务完成。
- 纯视觉样式修改通常不要求新增或运行功能测试，但应让用户人工验证。
- 最终说明只列出实际执行过的检查。未执行、因环境受限无法执行或仍然失败的检查必须明确说明。

> 但本项并不意味着你要为每一个细节都写重复且冗杂的测试用例，只写必要且有价值的测试即可，如果有一部分测试用例难以构造，则不需要进行构造只需要向用户说明此处没有构造测试用例，需要自行测试即可。

### 代码与文档风格约定

- 文档和代码注释遵循项目既有语言和格式约定。项目没有明确约定时，默认使用用户所使用的语言，代码标识符、配置键和公开接口名称使用清晰一致的英文命名。
- 沿用现有的代码风格、目录结构、依赖管理方式、构建工具和测试框架。除非有明确理由，不要在同一项目中引入重复或平行的实现方式。
- 优先做范围明确、可验证的修改。不要夹带无关重构，也不要覆盖工作区中与任务无关的已有改动。
- 修改配置、依赖、构建脚本、部署文件或生成文件时，应评估对本地开发、测试、发布和运行环境的影响。
- 每个独立功能或 Bug 修复都应形成可独立审查、验证和回滚的变更单元，例如独立提交、变更集或合并请求。
- 完成一个独立功能或 Bug 修复后，先运行相关测试和静态检查，再进入提交流程

### 提交规则

- 完成一个独立且已验证的变更后，应主动建议提交，但未经用户明确确认不得实际提交。
- 如果用户追加了与当前功能无关的修改，应先确认它们应属于同一变更单元还是分开提交。
- 提交时应简要说明主要变更、验证结果、已知限制、未执行的检查。
- Commit Message 风格应优先按仓库内的提交风格或者用户指定风格为准。
- 如仓库内 Commit Message 风格较乱，且用户没有明确说明提交风格，应该遵循 Conventional Commits：`type(scope): description`。
  - 允许的 `type`：`feat`、`fix`、`refactor`、`style`、`docs`、`test`、`chore`、`perf`。
  - `scope` 使用受影响模块的小写名称；多个模块用逗号分隔；无法确定时使用 `*`；不存在多个模块时可省略此部分。
  - `description` 使用小写、简洁地说明做了什么，不描述实现过程。
  - 示例：`feat(desktop): skeleton loaders for list/message loading states`。
